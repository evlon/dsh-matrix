## 修复：matrix 发送消息报 "id collision" / "already has a persisted log on disk"

### 现象
用户在 matrix 发消息 → `createRoomAgent` 抛：
`session "matrix-ai-niukunliang-5f33b677" already has a persisted log on disk that does not match this live session (id collision)`

### 根因
- dsh-matrix 用确定性 sessionId：`matrix-${localpart}-${stableHash(roomId)}`，同房间永远同一 id。
- 该 id 在磁盘已有持久化 log（之前此房间已对话过），`ctx.agents.create({sessionId})` 走
  `adoptLivePrefix`，要求本次 create 的 seed（live 会话创建时刻事件）逐字节等于磁盘已存全部前缀
  → 旧 log 累积了事件，新 seed 覆盖不了 → 抛 id collision。
- bridge.ts:422 原 catch 只覆盖 `already exists` / `while it is live`，**漏掉 `id collision` / `already has a persisted log`**。

### 修复
- bridge.ts `createRoomAgent` catch 分支扩展为：reason 含 `already exists` / `while it is live` /
  `id collision` / `already has a persisted log on disk` 任一即转 `ctx.agents.resume({resumeSessionId})`。
- 注释同步更新说明四种冲突都复用既有会话（不重建、不堆积多会话）。
- 验证：tsc 通过、node --test 全绿（2 passed）。

### 已知边界（次要，未动）
- resume 后 session.header.cwd 是磁盘旧值；若用户经 cwd 引导改了工作目录，agent 实际运行目录
  可能仍是旧值。header 只读、SessionStore 无公开 patch API，强行改 cwd 风险高。当前若未改目录无影响。
- 若后续要支持"改目录同步到已 resume 会话"，需走 meta/持久化层（不在本次范围）。

## 修复 #2：dsh web 启动报 "cannot prepare session ... while it is live"

### 现象
`dsh web` 启动瞬间 fatal：`cannot prepare session "matrix-ai-niukunliang-5f33b677" while it is live`
（dsh-session-persistence coordinator.ts:724，prepare 时 `ctx.sessions.get(id) !== undefined`）。

### 根因
- harness 内核在 `dsh web` 启动时会自动加载/恢复所有持久化会话使其成为 live。
- dsh-matrix 的入站消息（或启动后 Matrix 推送）触发 `getRoomAgent` → `createRoomAgent` →
  `ctx.agents.create`/resume。当内核已在加载或已加载该确定性 id 会话时：
  - create 走 adoptLivePrefix → 若内核已 live 则抛 id collision（上一轮错误）；
  - 改为 resume 后 → resume 也走 prepare → 撞 `while it is live`（本轮错误）。
- 本质：bridge 对同一 id 并发触发 prepare，与内核 auto-resume 抢同一会话。

### 修复（src/bridge.ts createRoomAgent）
1. **入口优先取用 live**：create 之前先 `ctx.agents.get(sessionId)`；若内核已加载该会话
   （返回 Agent），直接包成 `{agent, dispose:async()=>{}}` 取用，完全跳过 create/resume，不二次 prepare。
2. **create 失败 → 轮询等待内核 live**：catch 到 already exists / while it is live / id collision /
   persisted log 时，不再直接 resume（会二次 prepare 撞车），改调 `waitForLiveAgent()`：
   最多 ~1.8s 每 150ms 轮询 `ctx.agents.get(id)`，内核 prepare 完成即取用；都失败才最后 resume 一次兜底。
3. **history binding resume 失败**也走 `waitForLiveAgent` 兜底。
4. `asHandle(agent)` helper 把内核返回的 `Agent` 包成 `AgentHandle`（dispose: async noop），
   统一 roomAgents 缓存与 `return handle.agent` 逻辑。

### 验证
- tsc 通过。
- 测试 mock 补 `ctx.agents.get`（两测试文件）；`node --test` 全绿（2 passed）。

### 关键 harness 内核知识
- `ctx.agents.get(id)`：返回已 live 的 Agent，未 live 返回 undefined（不触发 prepare）。
- session-persistence `prepare(id)`：用 `preparations.reserve` 按 id 串行化，prepare 前查
  `ctx.sessions.get(id)` 防重复；内核自身不会双 prepare 同一 id（串行保护）。
- 所以纯启动报 while it is live 必是 bridge 触发了并发 create/resume；get 优先 + 轮询取用彻底消除。

## 修复 #3（最终治本）：id collision 因 cwd 不匹配 / 先 create 撞已有 log

### 现象（用户第三次反馈）
`⚠️ 本次会话因错误结束：...already has a persisted log on disk that does not match this live session (id collision)（UNKNOWN）`
会话运行中（非启动）报，且上一版（先 create 失败再轮询+resume 兜底）仍触发。

### 真正根因（coordinator.ts:1306 / 1312）
- 1312：`create` 走 `adoptLivePrefix`，要求本次 create 的 seed 逐字节等于磁盘已存前缀。
  会话已有历史 log → 新 create 的 seed 覆盖不了 → id collision。
- 1306：**更隐蔽**——`create` 时磁盘已持久化的 cwd 与本次 create 传的 `meta.cwd` 不同 →
  也抛 id collision。dsh-matrix 之前 create 传 `cwd: roomCwd ?? cwdCandidates[0] ?? process.cwd()`，
  与磁盘值（用户上次在 e:/oa 跑留下的 cwd）不一致即撞。
- 上一版 waitForLiveAgent 最后的 `resume` 兜底**无 try/catch**：resume 因 cwd 不匹配再次抛
  id collision → 直接冒泡 → 用户所见。

### 最终修复（acquireAgent 重写，src/bridge.ts）
顺序改为「先 resume（不传 cwd），resume 无 log 才 create」：
1. `ctx.agents.get(id)` 命中（内核已 live）→ 直接取用，绝不 prepare。
2. `ctx.agents.resume({resumeSessionId, agentOptions})`——**不传 cwd**，复用磁盘持久化 cwd，
   彻底避开 1306/1312 两类 id collision。已有 log 的会话正常续接。
3. resume 因「not found / no such / has no persisted」失败（全新会话）→ `ctx.agents.create`
   带 `meta.cwd`（roomCwd ?? cwdCandidates[0] ?? process.cwd()）。
4. resume 撞 `while it is live`（内核并发 prepare）→ 轮询 `ctx.agents.get` 等待内核注册后取用。
5. 其它 resume 失败先再轮询一次，仍失败抛原始错误（不再静默丢类型）。
- 内联 `waitForLive` helper（12×150ms 轮询）；`wrap(agent)` 把内核 Agent 包成 AgentHandle。
- history binding 路径保留：先 get → resume → while it is live 取用 → fallback 确定性 id。

### 验证
- tsc 通过；测试 mock 的 `ctx.agents.resume` 改为成功返回 handle（两测试文件）；`node --test` 全绿（2 passed）。
- 关键认知：**dsh-matrix 的会话一旦创建在磁盘就有 log，续接必须 resume 而非 create**；create 仅用于真·全新会话。

### 已知边界
- resume 用磁盘 cwd，若用户经 cwd 引导改了工作目录，resume 后 agent 实际 cwd 仍是旧值
  （header 只读，SessionStore 无公开 patch）。未改目录则无影响。后续若要支持"改目录同步到已 resume 会话"
  需走 meta/持久化层（不在本次范围）。

## 修复 #4：Matrix 数字分身回复工具 "unknown tool"（execute_command/read_file 不可用）

### 现象
用户在 Matrix 问数字分身能运行啥工具，agent 回复 execute_command / read_file 都是 "unknown tool"。
但 harness GUI 会话里这些工具可用。

### 根因
- harness 工具由 **agent preset** 决定：preset 通过 `ctx.agentPresets.mount(agentCtx, id)` 把
  shell/file/检索/skills 等工具的 cordis 注册 compose 到 agent 的 scope context 上。
- `mount` 必须在 agent factory 的 `setup(agentCtx)` 回调里调用（api-catalog.ts:1222 / 152）。
- GUI 会话由 host 高层 API 创建时**自动注入 setup** 挂载 preset；而 dsh-matrix 直接走
  `ctx.agents.create/resume`（底层 factory），**从未传 `setup`** → agent 不 compose 任何 preset
  → 工具完全不可见 → LLM 侧报 unknown tool。
- 关键佐证：config.ts 的 `agentPreset` 注释明确「缺省 standard 提供完整工具；留空则 agent 无任何工具」。

### 修复（src/bridge.ts）— 已 commit c440aed
- **正确做法**：`agentPresets` 是 host 平面服务（`@deepseek-ai/dsh-agent-presets` 注册），
  不在 dsh-matrix 插件 ctx 的类型声明里。直接属性访问 `this.ctx.agentPresets` / `agentCtx.agentPresets`
  都会触发 cordis `cannot get property "agentPresets" without inject`。
  改用 `this.ctx.get('agentPresets')` 动态获取 host 服务实例（绕过类型级 inject 声明），
  再 `presets.mount(agentCtx, config.agentPreset ?? 'standard')`。
- `acquireAgent` 的 `resume` 与 `create` 均加 `setup: this.agentSetup()`；history binding 的 `resume` 也加。
- 内核已 live 的 agent 由内核自己 mount，dsh-matrix 取用时工具已可用，无需重复；mount 幂等。

- tsc 通过；`node --test` 全绿。已 commit `c440aed`。
